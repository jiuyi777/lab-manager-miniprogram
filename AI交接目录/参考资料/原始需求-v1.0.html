一、项目背景与目标

1.1 背景

实验室现有仪器预约、试剂领用、样品登记等事务主要依靠纸质登记表、微信群口头协调或零散的 Excel 表格管理，存在以下痛点：

  • 时段冲突频发：学生到现场才发现仪器被占用，白跑一趟。
  • 台账不实时：试剂库存靠人工盘点，常出现"账上有、柜里没有"。
  • 审批链路长：请假条式的线下审批，管理员不在办公室就无法推进。
  • 无追溯：谁在什么时候改了什么，事后无法查证，责任不清。
  • 信息分散：仪器使用说明、安全须知只在墙上贴着，新人上手困难。

1.2 建设目标

  1. 预约线上化：学生手机端即可查看仪器实时状态、按时间段预约、收到审批结果通知。
  2. 状态可视化：仪器空闲 / 占用 / 维护状态用颜色一眼区分，无需询问。
  3. 台账实时化：试剂领用即扣减，库存临期与告急自动预警。
  4. 协作同步化：多位管理员同时在线操作，数据秒级同步，不产生脏数据。
  5. 知识沉淀化：仪器使用方法、安全须知、仪器档案线上化，新人可自助查阅。

1.3 范围边界

本期包含

  • 仪器预约全流程（查询 → 预约 → 审批 → 签到 → 归还）
  • 试剂台账与领用登记、库存预警
  • 样品登记与测试项关联
  • 实验室与仪器基础信息管理
  • 管理员审批台与操作日志

本期不含（后续迭代）

  • 仪器数据自动采集与图表分析
  • 与学校统一身份认证（CAS）对接
  • 消息推送到微信服务通知（先做小程序内红点）
  • 经费、耗材采购流程

层级选型说明
前端微信小程序原生（WXML / WXSS / JS）无需构建工具，代码包上传微信平台即可，便于校内维护与交接

准入校园网 WiFi 或校园 VPN天然满足区域限制与安全要求，校外无法访问
数据层后端数据库前端通过统一 API 层访问，便于 Mock 与真实接口切换
重要前提：微信小程序正式版要求请求域名必须为已备案的 HTTPS 域名。若校方服务器只有内网 IP，有两种方案：① 申请一个校内域名并配置 HTTPS 证书（推荐）；② 开发调试阶段在微信开发者工具中勾选「不校验合法域名」，仅用于测试，不能上正式版。

五、核心业务流程

5.1 学生预约主流程

选择实验室 → 浏览仪器列表（看状态颜色）
      ↓
   进入仪器详情（看使用方法 / 安全须知）
      ↓
   点击「选择时间段预约」→ 查看今日时间轴
      ↓
   选择起止时间 → 填写样品用途 → 提交
      ↓
  ┌─ 时段空闲 ────────────┐   ┌─ 时段冲突 ──────────────┐
  │  生成待审批预约单        │   │  弹出引导弹窗             │
  │  广播 booking:new       │   │  ① 改约最近空闲时段       │
  │  管理员待审批 +1        │   │  ② 查看今日完整时间表      │
  └───────────┬───────────┘   │  ③ 换一台同类型仪器       │
              │               └───────────┬─────────────┘
              ↓                           │
     管理员审批 ──驳回──→ 通知学生 + 填写原因  │
              │                           │
           通过 ↓ ←────────────────────────┘
     广播 booking:approved → 学生状态变绿
              ↓
     到约定时间 → 签到（记录 actual_start）
              ↓
     实验结束 → 管理员归还确认（记录 actual_end）
              ↓
     预约状态置为 completed，仪器释放为空闲
     广播 instrument:updated → 所有人界面刷新

5.2 试剂领用流程

学生打开试剂台账 → 选择试剂 → 点击「领用」
      ↓
   填写领用数量 + 用途 + 关联样品
      ↓
   校验：数量 ≤ 当前库存？
      ↓ 是
   扣减库存 → 写入 reagent_logs
      ↓
   广播 reagent:stock_changed
      ↓
   所有在线端库存数字实时更新
      ↓
   若扣减后低于阈值 → 首页「库存预警」+1，卡片转红

5.3 并发编辑保护流程

管理员 A 打开仪器编辑页（读取 version = 7）
      ↓
管理员 B 同时打开同一仪器（version = 7）
      ↓
   A 先保存 → 后端比对 version 一致 → 更新为 version = 8
      ↓
   B 提交 → 后端比对 version（7 ≠ 8）→ 拒绝
      ↓
   B 端提示：「数据已被 A 修改，请刷新后重试」
      ↓
   B 刷新拿到最新数据，重新编辑

六、多管理员实时协作机制

6.1 同步方式

场景机制
A 管理员新增仪器后端落库 → 广播 instrument:updated → B 管理员列表自动出现新仪器
A 审批通过预约广播 booking:approved → 学生「我的预约」状态自动变绿
A 修改试剂库存广播 reagent:stock_changed → B 的试剂页数字实时跳动
A 发布公告广播 announcement:new → 所有在线端顶部公告条刷新
并发编辑冲突数据表带 version 乐观锁，后提交者收到「请刷新重试」提示
WebSocket 断线前端每 30 秒轮询关键数据兜底，重连后自动恢复推送

6.2 设计原则

  • 不打扰：别人的操作不弹窗打断当前使用，只静默刷新对应区域；仅涉及当前用户的审批结果才提示。
  • 可见即可信：所有管理员操作写入日志，任何人可查「这条数据是谁改的、什么时候改的」。
  • 冲突不丢数据：乐观锁只拒绝后提交者，其填写内容保留在表单中，刷新后大部分可复用。

七、界面设计规范

7.1 三条设计原则

① 看板优先 —— 打开首页第一眼看到的是数字和状态，不是菜单。管理员每天最关心「有几件事等我处理」。

② 交通灯语义 —— 颜色即状态，用户不需要读文字说明就能判断「能不能用」。

③ 一键直达 —— 看板上的每个数字都是可点击入口，点「待审批 5」直接进入那 5 条记录，不做二级菜单。

7.2 色彩语义（全局统一）

所有页面共用一套语义色，不解释就懂。

翠绿　正常 / 空闲 / 已完成 · 仪器空闲、预约成功、库存充足
朱红　异常 / 占用 / 待处理 · 仪器使用中、冲突弹窗、库存告急、逾期
琥珀　警告 / 待审 / 即将到期 · 待审批、即将超时、保质期临近
靛蓝　操作 / 可点击 / 链接 · 主按钮、可跳转卡片
灰白　不可用 / 已归档 · 已停用仪器、已取消预约

八、页面详细设计

页面 1启动页 · 身份选择

应用的第一屏，承担品牌露出与身份分流两个职责。

顶部品牌区图标 + "实验室管家" + 一句话副标题
引导文案请选择您的身份
身份卡片 ×3学生 / 老师 / 管理员，各带一行权限说明
主按钮进入登录
网络提示未连校园网时显示琥珀色引导条

设计要点：三张身份卡片用各自角色的语义色描边（学生靛蓝、老师翠绿、管理员朱红），选中态明显。底部常驻提示「仅限校园网内访问」。

根据上一步选择的身份，动态切换输入项与提示文案。

学生学号 + 密码，提示"首次登录请使用初始密码"
老师工号 + 密码
管理员工号 + 密码 + 二次验证（可选）
辅助操作返回身份选择 / 忘记密码（联系管理员）

页面 3首页 · 角色自适应看板

全应用信息密度最高的一屏，用四个纵向区块组织。

顶部固定区（10%）标题 + 通知红点 + 个人入口 + 公告横向滚动条
核心看板区（30%）待审批 / 使用中 / 库存预警 三块大数字卡，点击直达
实验室卡片区（50%）每实验室一张卡：仪器数 + 空闲/占用/维护计数 + 今日预约
底部导航（10%）首页 / 预约 / 试剂 / 我的

看板区细节：数字 26px 换行居中，标签在上、数字在下、单位在最后。三块卡分别用朱红（待审批）、翠绿（使用中）、琥珀（库存预警）填充浅色底，形成强烈的视觉分区。

公告条：横向滚动，紧急公告使用朱红底色，普通公告使用灰底。点击展开完整公告列表。

学生视角差异：核心看板区替换为「我的今日预约」卡片与「快速预约」入口，实验室卡片区保留。

十、数据库表结构

以下为建议表结构，后端可据此建表。字段类型按常规关系型数据库约定。

users           id, name, role(student|teacher|admin), student_id, employee_id,
                password_hash, lab_access[], created_at, updated_at

labs            id, name, code(501/502), location, manager_id, open_hours,
                status(active|maintenance|closed), sort_order, version

instruments     id, name, model, lab_id, code, photos[], manual_text, manual_file,
                safety_notice, source, purchase_date, lifespan_years,
                status(idle|occupied|maintenance|disabled), needs_approval,
                requires_training, location_detail, next_calibration_date,
                version, created_at

bookings        id, user_id, instrument_id, start_time, end_time, purpose,
                status(pending|approved|active|completed|cancelled|overdue),
                actual_start, actual_end, checked_in_at, returned_at,
                reject_reason, version, created_at

reagents        id, name, cas_number, specification, concentration, location,
                current_stock, unit, safety_level, expiry_date,
                low_stock_threshold, version, created_at

reagent_logs    id, reagent_id, user_id, quantity_used, purpose, sample_id,
                used_at

samples         id, code, name, user_id, composition, process, target_tests[],
                version, created_at

sample_files    id, sample_id, file_name, file_url, uploaded_at

announcements   id, title, content, priority(normal|urgent), created_by, created_at

notifications   id, user_id, type, title, content, ref_id, is_read, created_at

operation_logs  id, user_id, action, target_type, target_id, detail, created_at
建表必读：labs / instruments / bookings / reagents / samples 五张表必须包含 version 字段，用于多管理员并发编辑的乐观锁校验。这个字段必须在建表阶段预留，后期补加会导致历史数据无版本号，并发保护失效。更新时 SQL 应写成 UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?，受影响行数为 0 即代表冲突。
